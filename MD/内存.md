大小端序的最小翻转单位是字节（8 bit），字节内部的比特排列对所有平台都是一样的
比如写入 0x12345678 四个字节存入 大于1个字节（左边是高位）
收到主机序影响 因此会写入内存 
由于pc小端序 低地址低位高地址高位
因此查看就是

78 56 34 12

//收到网络序
#define PEEK_U32(p) \
	(((uint32_t)(((const u_char *)(p))[0]) << 24) | \
	 ((uint32_t)(((const u_char *)(p))[1]) << 16) | \
	 ((uint32_t)(((const u_char *)(p))[2]) << 8) | \
	  (uint32_t)(((const u_char *)(p))[3]))


考虑场景 
网络字节序都是大端序
因此假设 
数字真实内容为16进制表示：0x12345678
那么 大端序 是低址高位  高址低位 符合人类书写顺序

p[0] 地址就是高位12 
因此p[0]<<左移就是高位处理 最后直接就变成了 0x12


```
内存（RAM）层面——大小端有差异
同一个文件 0x270F 写入内存：
x86 小端：  0F 27   （低地址 → 高地址）
大端机器：  27 0F   （低地址 → 高地址）
两台机器内存里的字节排列不一样。

寄存器层面——统一，无大小端概念
数据从内存读进寄存器之后，CPU 会自动按本机字节序重组，寄存器里的值永远是：
寄存器：  0x0000270F
```

大小端问题本质上是内存和寄存器之间搬运字节时的映射规则，一旦数据进了寄存器就不存在大小端之分了

寄存器内部都是左高右低

//转网络序
#define POKE_U32(p, v) \
	do { \
		const uint32_t __v = (v); \
		((u_char *)(p))[0] = (__v >> 24) & 0xff; \  
		((u_char *)(p))[1] = (__v >> 16) & 0xff; \
		((u_char *)(p))[2] = (__v >> 8) & 0xff; \
		((u_char *)(p))[3] = __v & 0xff; \
	} while (0)

这是因为第一步骤复制就已经给到寄存器了？
是的，正是因为 __v 完美符合了局部的、只读的、生命周期极短的、不取地址的特征，它才得以成为纯粹的寄存器化身。

用编译期的硬核铁律去消灭由于“权限不清”和“命名污染”带来的全方位心智损耗。

不透明指针，本质上就是 C 语言在“没有私有化语法”的物理限制下，强行利用“编译器只凭名字无法计算大小和偏移”的硬核原理
c++可以通过权限控制去管理 Private 等不暴露 这样引用头文件只能用不能改


C++ 的 private 在成品二进制层面根本没有防御力。它唯一的防线，就是在你手握源码进行编译的那一秒钟
开发阶段控制 防止多人开发误操作
```
#ifndef SESSION_H
#define SESSION_H

// 1. 前向声明（Forward Declaration）：告诉编译器有这个结构体标签，但现在不告诉你长啥样
typedef struct net_session net_session_t;

// 2. 所有接口都只能基于这个不透明指针（Handle）进行操作
net_session_t *session_create(int port);
void session_process(net_session_t *s);
void session_destroy(net_session_t *s);

#endif
```
